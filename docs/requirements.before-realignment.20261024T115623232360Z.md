## 2. 当前子任务的要求

**T01：静态地图接入与坐标转换验证。** 这是本次提出的第一子任务划分，**待决策**，不表述为此前已经单独确认。

选择这一范围的原因：静态地图来源已明确，可以先验证 ROS 数据与现有算法地图表达能否对应；MPC 和动态层协议尚未明确，不必让它们阻塞这一小步。

本子任务拟包含以下能力，具体实现须在范围和必要输入明确后开展：

1. 在 Humble 环境构建并启动最小地图接入程序，接收现有 `map_server` 的静态地图；启动顺序不应导致遗漏已发布地图。
2. 检查地图尺寸、分辨率、数据长度、frame 和原点姿态，形成一份元数据与栅格内容一致的地图快照。
3. 按已确认的发布端编码转换成算法所需的地图表达，明确哪些格可通行、哪些格不可通行；编码或未知策略未确定时，不暗中猜测。
4. 验证“地图坐标点 ↔ 地图局部坐标 ↔ 格索引”的转换，保证方向、原点偏移和边界处理一致。
5. 能输出地图元数据、转换状态及少量验证点的结果，支持与实车原始地图核对。不要求为此新增自定义 ROS 消息。

本子任务的结果是**经过验证的地图输入与坐标适配**，不输出可执行路径，不要求启动车体运动。A* 搜索、平滑、车体膨胀、动态融合、MPC 下发和性能优化分别留给后续子任务。

当前这一轮交付仅为本需求文档；上述程序和验证是子任务后续实施内容，不表示本轮已获指令开始编码。

## 3. 输入输出及单位

| 类别 | 内容 | 单位及解释 | 确认状态 |
| --- | --- | --- | --- |
| 输入 | 静态地图消息 | 建议按 `nav_msgs/msg/OccupancyGrid` 接入；实际类型、话题、QoS 查发布端 | 待核对 |
| 输入 | width、height、data | 宽高为格；数据长度应等于 width × height；行主序索引为 `y * width + x` | 消息约定，适用前提是确认该消息类型 |
| 输入 | resolution | m/格，期望默认 0.05；实际读取消息，不能仅靠写死默认值 | 默认值已确认 |
| 输入 | header.frame_id、stamp | 坐标系名称；ROS 时间戳；保留发布端信息 | 实际值待核对 |
| 输入 | info.origin | 第一个格左下角在消息 frame 中的位置与姿态；位置 m，二维角度 rad | 实际数值待核对 |
| 输入 | 栅格取值 | 占用编码，无量纲；空闲、占用、未知和中间值按实际发布配置解释 | 待核对，策略待决策 |
| 验证输入 | 少量地图坐标点 | x/y，m，注明所处 frame；只验证转换，不作为运动目标 | 可随地图一并确定 |
| 内部输出 | 算法地图与元数据快照 | 建议二值表达 `0=障碍、255=可通行`，配套宽高、分辨率和原点变换；不是新发布协议 | 建议，待决策 |
| 验证输出 | 格索引与反算位置 | 索引为整数格；位置 m；明确反算使用格中心或角点 | 代表点约定待决策 |
| 状态输出 | 等待地图、转换成功、拒绝及原因 | 先用日志/现有诊断方式即可，不包含导航成功或到达状态 | 具体形式可按实现选择 |

代码事实：`YAstar::setMap(uchar*)` 与 `SfcSquare` 地图以 0 为障碍；`YAstar::setMap(vector<int8_t>)` 则仅 0 可通行，其余均占用。不能将 ROS 原始占用数组不经解释就交给不同接口。证据为 `tdt-nav-kit/src/YAstar/yastar.cpp:404,418` 和 `src/MinimumSnapOsqp/sfcSquare.cpp:14`。

坐标转换要求：使用地图原点的逆变换得到局部位置，除分辨率后向下取整；ROS 消息接入不照搬 PNG 示例的 Y 轴翻转。`map` 坐标系和地图 `info.origin` 不等同，不能因为存在 TF 就把原点偏移省掉。本子任务只处理地图自身 frame，不要求接入整条 LIO/机器人 TF 链。

## 4. 边界条件

| 条件 | 本子任务预期行为 |
| --- | --- |
| 尚未收到地图 | 保持等待状态，不构造伪地图；核对实际订阅 QoS |
| 空地图、数据长度错误、分辨率非正或非有限 | 拒绝并说明原因，不读越界内存 |
| 无效 frame、原点坐标非有限、无效四元数 | 报告输入无效；允许的姿态与归一化容差在实现时明确 |
| 非零/负原点、非 0.05 分辨率 | 按消息元数据计算，不能按示例零原点和 20 格/m 硬编码 |
| 点位于图外或恰好越过上界 | 索引须满足 `0 ≤ x < width`、`0 ≤ y < height`；略小于局部零的点不能因整数截断落到第 0 格 |
| 原点有 yaw 旋转 | 支持完整二维变换，或明确拒绝并报告原因；支持范围待决策，不能忽略旋转后继续转换 |
| 原点有非平面姿态 | 本项目是二维算法，不静默当作普通二维地图；接纳范围待核对 |
| 未知格或中间占用值 | 按已决定的策略处理；策略未定或编码不符时明确报告，不当成已确认空闲 |
| 地图尺寸或原点更新 | 元数据与栅格内容整体替换，不混用不同次消息的数据 |
| 当前静态地图未膨胀 | 保留并注明“未膨胀”；本子任务通过不代表路径已具备车体净空 |

## 5. 验收标准

以下为 T01 范围确认后的拟定标准，不要求完成整个规划系统：

1. 在 Humble 环境可重复构建、启动、退出；不依赖 OpenCV 窗口、按键或示例图片相对路径。
2. 使用实机 `map_server` 数据，核对宽高、分辨率、frame 和原点；接入程序后启动仍能按发布端协议获得地图。
3. 在已决定的占用策略下，原图选定的空闲格与障碍格转换正确；不转置、不上下翻转、不反转障碍含义。
4. 至少核对地图内部、四侧边缘、图外和非零原点的转换；若支持旋转，再核对旋转地图。格中心反算回索引应一致，格边界点按约定归属，不能要求任意点量化后仍精确还原原位置。
5. 对空地图、错误长度、非法分辨率和未支持姿态明确报错，不崩溃、不产生成功状态。
6. 记录实际命令、输入地图元数据、验证点及结果，能判断通过与否；边界可对适配逻辑做小规模数据验证，不需要仿真或车体运动。

完成时交付最小接入实现及运行方式、必要参数、验证记录。文档与记录仍位于原项目目录之外；源码实施位置在编码前另定。地图文件和现场验证尚未提供，因此现在不能宣称这些标准已通过。

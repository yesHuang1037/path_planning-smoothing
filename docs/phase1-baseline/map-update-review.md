## 1. 结论与范围

当前主要问题不是话题名称错误，也不是动态图把静态图清掉，而是：**新规划器收到实时地图 updates 后，没有更新保存的实时地图，反而清除实时地图和路径，导致后续目标无法开始规划。**

进一步复核确认，还有两个独立问题：**即使始终发送合法整图，成功发布的路径也会被下一张整图清空；反过来，地图完全停止更新时，已发布路径又不会因超时自动清空。** 因而不能只补updates，也不能只改上游持续发整图，更不能简单删除所有清空操作。

本次拟改进范围为新隔离工作区的地图接收、地图有效性判断、路径复检和相关状态提示。继续复用现有地图融合、A*、化简与QP核心；不重建导航系统，不修改原导航、SLAM、MPC或TDT工程，不覆盖备份，不开启底盘执行。

**同步方案核实后的技术建议：**本机Nav2 1.1.20的updates时间戳为零，首次晚订阅可能漏掉中间更新，滚动后还可能回放旧updates。仅靠现有两个话题及最近整图，不能建立足够可靠的同步关系。为保持已确认的OccupancyGrid话题/编码，建议第一阶段采用“持续发布实时整图”的方案B；这需要用户另行同意上游启动配置变更，本轮没有执行。现成的`costmap_raw`整图输出是无需修改上游的备选，但需确认更换输入话题/类型及编码适配范围，不能静默替换。详细证据见第6.1.1节。

## 2. 三个话题各自的作用

| 话题 | 内容 | 正确用途 |
| --- | --- | --- |
| `/map` | 场地静态底图，包含固定障碍 | 单独保存，作为规划的基础 |
| `/costmap/costmap` | 机器人周围实时地图的整张数据，包含位置、尺寸、格子大小和全部格子 | 建立或替换实时层 |
| `/costmap/costmap_updates` | 周围地图某个矩形区域的新格子数据 | 修改已保存实时层中的对应区域 |

后两个话题是**同一实时地图的两种发送方式**，不是两层独立地图。“整张地图”不等于整个场地：例如周围8×8 m、每格0.1 m的地图，整图是80×80格；updates只发送其中变化的一块。

规划时使用“静态底图＋有效实时层”。实时空闲格不能清除静态墙体；实时障碍消失时只移除实时层贡献。实时窗口以外保留静态层，不假装已经感知到自由空间。

### 2.1 周期与接收方式

所查上游启动文件配置内部更新和对外发布均为10 Hz，即约0.1 s一次计算/发布机会；不代表两个话题分别固定10 Hz。整图与增量的实际选择还取决于发布器实现、地图位置或尺寸变化、订阅情况和运行负载。

规划器按消息到达触发处理，不另设地图接收周期。当前订阅代码中的`10`是队列深度，不是10 Hz；节点20 ms定时检查也不是地图更新或重新规划周期。

### 3.1 四个回调和`poll()`的准确执行关系

| 事件 | 清路径 | 清除/替换地图 | 是否取消已有计算、安排新计算 |
| --- | --- | --- | --- |
| 静态图到达 | 是，内容相同也清 | 先清`base_`，转换成功后恢复；不清`dynamic_` | 不取消计算，不自动安排新计算 |
| 实时整图到达 | 是，内容相同也清 | 先清`dynamic_`，转换成功后立即恢复并刷新时间；不清`base_` | 不取消计算，不自动安排新计算 |
| updates到达 | 是 | 清`dynamic_`且不恢复；不清`base_` | 不取消后台计算，但使结果检查或新请求检查可能失败 |
| 新目标到达 | 是，用于撤销旧路径 | 不改地图 | 增加目标编号并保存最新目标；旧计算不被中断，完成后因目标编号不符被丢弃 |
| `poll()`每20 ms触发 | 不会无条件清空或重发路径 | 不主动更新地图 | 收取已完成结果，或者为待处理目标启动一次计算 |

以上为默认`static_only=false`；静态调试模式会跳过两个实时地图回调，不能用该模式证明实时输入已接通。

**不能得出“清空操作导致任何情况下都无法发布”的结论。** 原因如下：

1. `main()`调用`rclcpp::spin()`，这些回调和定时检查在当前默认单线程执行器上串行处理。合法整图回调中的`reset → convert → 赋值`结束后，`poll()`才会运行，不会在二者之间插入并看到短暂空值。若转换失败，空值才会保留。
2. 搜索在`std::async`中使用按值捕获的快照；回调清空输出不修改该快照，不取消这个任务。地图回调也不增加目标编号。
3. 只要计算结束时最新输入有效、目标编号一致、起点漂移检查和最新图路径检查通过，`poll()`仍会发布一次结果。
4. 发布后下一次地图回调又会发空路径。没有新目标时，`poll()`没有任务可做，不会自动重发刚才的结果。

准确的两条故障链应分别描述为：

```text
整图＋updates：updates使实时图不可用 → 目标被拒绝或结果被丢弃
持续合法整图：能够计算并发布 → 下一次整图清掉显示 → 没有新目标就不恢复
```

### 3.2 原文未充分说明的输出与保护缺口

- 节点没有保存“当前已发布路径”供后续地图更新复检；`result`只是`poll()`中的局部结果。仅移除清空调用不会自动获得后续安全检查。
- `fresh()`仅在处理目标、接收计算结果和发布前检查。没有目标、没有计算结果时，`poll()`在`if (!pending_) return`处退出，不主动判断现有输出是否过期。
- 计算尚未结束时，`poll()`还会更早返回。后续加入超时/有效性检查时，必须放在这种返回之前，不能被正在求解的任务跳过。
- 三条Path输出目前都是默认非保留发布：晚加入的RViz订阅者不会自动收到此前发布的非空路径。持续地图回调还可能只让它收到空路径。
- 新目标会使旧结果失效，但不会立刻启动并行的新搜索；当前只允许一个后台任务，最新目标等待旧任务完成。
- 最终路径检查调用`latest.pathSafe(result.path)`未传入截止时间，其默认截止时间为最大值。节点只在整次检查完成后比较耗时；环境构建同样没有可中断预算。不能将当前实现描述为已保证及时的独立监控。
- 复检覆盖的是最终优化路径；原始/化简路径为算法过程调试数据，不能因最终路径通过就宣称另外两条也针对最新地图逐条复检通过。

#### 判断：什么已经可以排除

- **不采用“收到updates直接套到最近整图，再刷新有效时间”作为完整同步方案。** 上述晚订阅与滚动缓存反例已足以证明这种做法存在错误，不需要等实机出现事故才承认缺口。
- 不采用“按updates时间戳排序/配对”的方案，因为此版本该字段恒为零。
- 不把扩大接收队列、改成reliable或transient_local当作同步修复；它们不能凭空补齐晚启动之前的全部更新，跨话题也缺少绑定依据。
- 不把“读一次完整图服务，然后继续套updates”视为已解决：请求期间仍可能更新，服务响应与updates之间没有共同编号。
- 原导航常规顺序下能够工作，不等于其晚启动、滚动、重启边界已可靠；接收端保守等待并非毫无原因，但应提供明确可运行的输入模式，而非无限等待。

因此，A并非“绝对不能使用标准消息”，而是**目前已确认的这两个发布流不足以实现本阶段要求的可恢复同步**。要继续采用A，必须新增已验证的同步约束或接缝，不能只补一条矩形复制函数就宣称完成。

#### 本阶段推荐：B，全量OccupancyGrid输入

在已确认的现有话题、类型和编码范围内，建议采用B作为首期非驱动接入：

1. 经用户确认后，在实际启动配置中设置`always_send_full_costmap=true`，使发布器在初始化时取得该值；重新配置/启动后实测，不只查询参数值。
2. 保留`/map`静态底图，实时层只以每条自包含的`/costmap/costmap`替换，不再依赖updates拼接；几何变化随该条消息一起处理。
3. 接收端采用明确的“全量模式”，不混合增量。刚启动/切换期间的旧缓存updates不参与融合、不续期、不触发清空；以新鲜合法整图建立就绪。若长期没有整图则超时失效，不能悄悄退回增量模式。
4. 第6.4节当前路径缓存、内容变化复检、主动超时撤销仍必须一起实现。只开启全量发布不修这些逻辑，路径仍会被下一帧清掉。
5. 80×80格、10 Hz时，单格数据本身约64,000字节/秒，不含消息头、DDS和重传；这只是估算。现场核对CPU、实际频率和延迟，不能把估算当作性能验收。
6. 该方案解决的是实时图的完整性与位置对应问题，不能单凭整图时间戳证明传感器活跃。发布函数会重新打时间戳，TF获取失败时更新循环也可能继续调用发布；后续执行前仍需另验感知健康与停止保护。

**本轮只是技术建议收敛到B，没有修改外部配置，也没有擅自认定已取得修改授权。** 上游当前未运行，B在实际SLAM链路上的发布频率、编码、负载和感知失效场景仍待用户允许后验证；同步方案的源码与安装库依据已明确，不再以“尚未查清发布器行为”为由搁置。

#### 若不允许改上游：现有raw整图作为备选D

安装库已经提供`costmap_raw`整图输出，并非要求重写上游。按当前命名空间预计为`/costmap/costmap_raw`；本轮无活动实例，因此该实际话题名及端点须启动后核实。它每条消息携带完整格子、origin、尺寸和分辨率，可直接避免整图/updates拼接。

但它使用`nav2_msgs/Costmap`，数据是0～255的原始代价，不是现有OccupancyGrid的-1/0～100。若选D，需要用户明确同意输入接口的小范围变化，增加解码并保持已有阈值语义：254→100、253→99、255→-1，1～252按发布器转换表映射至1～98，0仍为0；不能直接沿用`raw >= 65`或简单除以254。第6.4节输出生命周期修复和感知健康边界同样不能省略。

因此D是已有接口的可选适配，不是本轮静默启用的方案；若坚持不改上游，它比在零时间戳updates上猜测同步更合适。

### 6.1.2 方案选择汇总

方案选择：

| 方案 | 使用条件 | 代价与边界 |
| --- | --- | --- |
| A：适配现有整图＋updates | 当前已发现晚订阅与窗口移动反例；仅凭现有流不能批准简单拼接 | 如要继续，必须补充经过验证的同步依据，不以普通QoS替代 |
| B：持续发送实时整图，当前首期推荐 | 经用户确认调整实际启动配置，保持OccupancyGrid话题/类型/编码 | 实现简单、传输更多；需确认全量刷新与感知健康，不等于已完成updates支持 |
| C：补充明确同步接口 | A不足且不采用B，另行确认接口范围 | 复杂度增加，不在本轮擅自扩展；仍需定义丢失恢复与健康判断 |
| D：接收已有raw整图 | 不改上游，但需用户确认输入类型和编码适配；活动端点待核实 | 同步不依赖updates；需精确转换代价编码，不擅自扩大已确认接口 |

本轮技术建议为B，而不是继续把A视为缺少调查的默认路线；B需要修改外部启动配置的授权。若用户不允许改上游，则明确确认D的接口变化范围，不静默切换。C仅在确有增量带宽需求等理由时另行设计，不作为首期默认扩建。

**建议落地顺序：**先确认B的上游最小参数变更权限（或明确选择D），在隔离环境一起完成自包含整图输入、路径缓存/复检和主动失效处理，再接真实SLAM做非驱动验收。即使采用B，也不能认为持续整图本身就是完整解决方案。

### 6.2 实时地图维护

同步规则确认后，复用或小幅扩展现有`DynamicGrid`：

| 输入/事件 | 建议处理 |
| --- | --- |
| 合法实时整图 | 验证后整体替换实时层，移除旧实时层贡献；保留静态底图 |
| 已确认对应当前地图的合法updates | 在原生实时格上修改矩形区域，再按完整面积融合到底图 |
| 未有整图就来updates | 不建立虚构底图，不视为就绪；等待明确同步 |
| 长度、边界、编码、frame或对应关系异常 | 不部分写入、不刷新健康时间；撤销不可信实时层的使用资格并等待恢复 |
| 静态地图变化 | 不混用旧快照；使相关候选失效，重建环境，重新核对实时层对应关系 |
| 长时间未确认输入健康 | 拒绝新规划或撤销有效结果，不因最后一张整图仍在内存就默认安全 |

每次搜索仍使用固定地图快照，接收更新不得在求解期间直接改写该快照；结果发布前使用最新可信地图复检，保留目标编号和起点漂移检查。

### 6.3 有效期与健康判断

将“地图内容是否同步”和“输入是否足够新”分开判断：

- 地图同步：是否有可信整图，后续更新是否能正确应用。
- 输入新鲜度：消息时间、接收时间及上游健康证据是否满足要求。
- 只有成功验证并应用的更新，才可刷新相应记录；无效、重复、过旧或无法对应的数据不能续命。
- 初次从缓存收到的旧整图不能仅靠本机接收时间变成新数据。
- 无变化时健康如何确认，须依据上游实际行为选择；必要的额外健康接缝需先确认范围。
- 当前0.5 s仅是调试初值；不以放宽超时掩盖同步错误，不把它当作已验证的实机停车参数。

### 6.4 路径发布和显示

**审查提案：**不再把“收到任意地图消息”直接等同于“必须清空路径”，改为依据输入可信度和路径复检结果决定。这是发布行为调整，须和地图接收修复一起验收，不能只删除`clearOutput()`。新目标仍先撤销旧结果，非法输入和不安全路径仍保持保守处理；不是一律取消四个回调的清空。

最小必要实现职责如下，名称表示职责，不要求新增通用框架或照搬为类名：

1. **输入回调只负责验证、保存和标记变化。** 相同合法静态图不引发重复清空；相同内容的实时整图可刷新输入时间，但不重复撤销路径。区分“收到新消息”和“地图内容/几何真的变化”，不能把消息计数直接当作路径失效条件。
2. **保存当前最终路径及其对应目标。** 记录检查过的地图内容版本和有效状态；有了该记录，才能处理后续更新和撤销。保留底图与实时层的独立所有权，不让输入回调修改正在计算的快照。
3. **统一处理输出生命周期。** 收到新目标、地图不可用、检查发现碰撞、超时或无法在期限内确认安全时，明确撤销；正常接收相同整图不能擦掉结果。没有新目标时不自动重新搜索。
4. **把健康检查放在`poll()`所有提前返回之前。** 即使没有目标、没有求解结果或已有求解仍未完成，也要处理输入过期和输出失效。不得把保护逻辑仅写在结果分支里。
5. **内容变化后进行有预算的路径复检。** 复用已有碰撞检查，但传入实际截止时间；环境构建也要有规模/耗时控制或移出接收回调，不能在地图回调中无限阻塞。必要时单独安排有界检查任务，不与已有QP任务排队互相饿死。检查期间标明尚待确认、不续有效资格；失败、超时或无法跟上更新则保守撤销，而不是一直以“检查中”保留有效状态。
6. **保持快照与新输入的一致性。** 检查结果对应的内容版本已过时，就不能确认新版本安全；内容完全相同的整图刷新不必因此作废。持续变化时允许合并待检查更新，但不能丢失最终完整状态或无限推迟失效处理。所谓“最新图”只能指当前已接收并验证的状态，不能把仍在接收队列中的消息当作已检查；需同时控制积压并核对消息年龄。

这些职责可以在现有节点内小幅组织实现；无需为此重写A*、QP或整个执行链路。当前单线程回调之间不存在“整图reset到一半被poll插入”的竞争，不能用切换多线程执行器来修复本问题，那反而需要新增共享数据同步。

| 状态 | 建议行为 |
| --- | --- |
| 地图可信且更新后路径仍安全 | 可保留调试显示；不因更新消息本身自动重新搜索 |
| 新障碍影响路径，或无法在预算内确认安全 | 清空当前有效路径，明确报告原因，不自动绕行/恢复 |
| 地图失同步、过期或坐标无效 | 清空有效路径并报告输入原因，禁止继续把旧路径当作当前有效结果 |
| 求解期间地图变化 | 不必因每次合法更新无条件作废；发布前用最新可信地图检查，不通过则拒绝交付 |
| 历史路径仅供对照显示 | 如确有需要，应另作明确标识，不与有效输出混用；本轮不默认新增历史显示话题 |

保留路径需要有不被QP阻塞的检查机制、明确检查预算和失效响应；在该机制完成前，不取消保守失效行为以换取“看起来有路线”。当前仍是调试Path，清空显示不等于机器人停车，S4执行保护另行完成。

RViz应添加`/snapshot_planner/optimized_path`的Path显示，Fixed Frame为`map`；可用不同颜色对照原始和化简路径。显示层订阅正确与规划层产生非空路径分别验证，不将调试路径重映射到`/sPath`来绕过执行接缝。

晚订阅显示可选择保留最新一条输出（发布端与RViz端都配置匹配的`transient_local`），或仅对“当前已检查且仍有效”的缓存路径做显示重发，二选一即可。**这必须在主动过期撤销完成后再做**：只增加缓存或反复重发，会让旧路径更容易被误认为有效。无论哪种方案，失效时的空路径也必须覆盖旧输出；不能把重发误当作重新检查。

### 6.5 目标和状态提示

建议把泛化错误拆为可直接排查的原因：缺静态图、缺实时整图、等待同步、实时输入过期、更新非法、TF异常、路径被新障碍否决。

首次输入就绪前保留一个最新待处理目标，按现有需求在输入就绪后处理；新目标覆盖旧目标。已经失败或失效的请求不周期重试，不因障碍消失自动重规划。若要扩大到“运行中断流恢复后自动执行旧目标”，须另行审查，不能混入首次就绪等待逻辑。

## 7. 实施顺序与验证清单

以下均为待完成项，不预填通过。合成输入只在隔离域运行，不向实机domain注入测试地图或目标。

1. 本轮安装库与同版本源码核实已完成；审查B的最小外部参数变更权限，或明确确认D的输入适配。活动上游恢复后另存实际参数和短时消息证据，不将历史活动值当作当前值。
2. 将第4.1节实验转为正式回归测试，先复现“曾经有路线但下一帧被清空”与“过期不撤销”，补齐接收与同步规则测试后再改入口；复用地图容器，不改搜索/平滑主算法。
3. 一起完成输入维护、当前路径缓存、有界复检和主动过期处理，再取消正常地图消息的无条件清空；补首次目标等待和状态区分，不单独解除保护或只改输出保留方式。
4. 复跑核心和隔离ROS测试，再接真实地图做非驱动验证，最后核对RViz。通过本项不代表允许启动MPC或底盘。

| 必测场景 | 验收要点 |
| --- | --- |
| 首次整图＋连续合法updates | 能维护实时地图，不再每条更新发空路径；有有效目标时能进入规划 |
| 持续10 Hz相同整图、重复静态图 | 不仅曾经出现非空路径，后续多个更新周期也不能被无故清空；不自动重复搜索 |
| 未有整图先收到updates | 不误用、不崩溃，等待同步，状态清楚 |
| 障碍添加、移除、整图替换 | 实时障碍正确变化，旧实时障碍不残留，静态墙始终保留 |
| 粗实时格与细底图相交 | 完整面积保守覆盖，不能只投格子中心 |
| 窗口移动及尺寸/位置变化 | 无旧更新错位写入；重同步规则有可验证依据 |
| 非法长度、越界、错误编码/frame | 原子拒绝，不部分写入、不刷新健康时间 |
| 乱序、重复、消息积压、上游重启 | 按明确规则处理，不把不可信数据当新地图 |
| 只有updates持续、没有新整图 | 同步规则允许时保持可用；不能仍按最后整图时间机械过期 |
| 地图不变但无变化消息；真实断流 | 能区分或明确无法区分的边界，不无限保留旧地图有效性 |
| 成功后无新目标、输入超时 | 无需再发目标也能撤销旧输出并报告原因；求解进行中同样不能跳过检查 |
| 求解中更新、更新后路径碰撞 | 发布前复检；不安全结果不发布，不自动重规划 |
| 求解较慢、复检超预算、输入变旧 | 保护处理不被长期阻塞，明确失效而非继续保留有效资格 |
| 首次地图未就绪目标、新目标抢占 | 仅保留最新待处理请求，旧结果不交付；不引入周期失败重试 |
| RViz显示 | 收到非空最终路径，坐标系正确；清空与失效原因一致 |
| 晚加入显示、失效后重新打开显示 | 有效结果按选定方式可见；失效后不能收到仍被当作有效的旧缓存 |
